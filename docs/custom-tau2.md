# tau2-bench, straight from upstream

`scripts/custom/run_tau2_bench.sh` runs [tau2-bench](https://github.com/sierra-research/tau2-bench) as upstream ships it, with nothing of ours in between: any tag, branch or commit of the repository (`--git-ref`, default `v2.0.0`), the dependencies upstream's own `uv.lock` pins, and every domain that ref has. At `v2.0.0` those are `mock`, `airline`, `retail`, `telecom`, `telecom-workflow`, `banking_knowledge` and `intake`. The defaults are tau2-bench's own, not a leaderboard's protocol.

```bash
scripts/custom/run_tau2_bench.sh --domain retail --model <served model> \
  --api-base-url "$EVAL_API_BASE_URL" --num-tasks 2
```

- **Install.** In the [prebuilt eval image](lm-eval-harness.md#prebuilt-evaluation-image-no-installs-at-run-time) upstream's checkout and its dependencies are baked in at the ref of `requirements/tau2-upstream.commit` (v2.0.0): nothing is installed or downloaded at run time, and `--git-ref` must name that ref or its commit (another ref, or `--repo`, is refused). Outside the image the ref is checked out into a cache keyed by its commit (`${EVAL_ENV_CACHE_ROOT:-$SCRATCH/eval-envs}/tau2-upstream`, `--cache-dir` to move it) and `uv sync --frozen --extra knowledge` installs it on Python 3.12 into the checkout's own `.venv`; that needs `git`, `uv` and network access the first time a commit is used. Our own lock does not come into it: upstream's `uv.lock` and the ref are the version. A bump of the image's tau2-bench is a change of `requirements/tau2-upstream.commit` (and so a new image).
- **Models.** The model under test is reached like `run_inspect_eval.sh` reaches its model (`--api-base-url`, key `TARGET_API_KEY`, else `CSCS_SERVING_API`). The key is never written into tau2's arguments: they carry `api_key: "os.environ/TARGET_API_KEY"` (litellm reads it at call time), so `results.json` and `--verbose-logs` hold no key. The simulated user is the same model on the same endpoint unless `--user-llm` says otherwise, at `reasoning_effort: low` with `max_tokens: 4096` (at the model's default effort a user turn sometimes ran 15k tokens and ended with no reply, which tau2 rejects and retries the whole task); `--user-llm-args` overrides both. A bare `--user-llm` name uses litellm's own credentials and gets neither. `--user-api-base-url <url>` reaches the user on an endpoint of its own (`--user-llm openai/<served name>`, a model other than the one under test; key `USER_API_KEY`, default `local`, as for the judge), keeping the low effort and the cap; `chonk_sft` puts every model's user (and retail's judge) on a gpt-oss-120b launched in a job of its own (below), because Apertus 1.5 as its own user rarely wrote the stop marker and the conversations ran to `max_steps`, and the shared API allows 15 requests a minute, far too few for a user that answers every turn. Sampling and thinking flags are the other launchers' (`--temperature`, `--top-p`, `--sampling-profile`, `--enable-thinking`, `--reasoning-effort`) and apply to the agent only (the user's effort is the pin above); tau2 sends no sampling setting unless you pass one.
- **The judge.** retail scores 112 of its 114 tasks partly with NL assertions (40 of them carry assertion text), which tau2 has an LLM check against the finished transcript. Upstream hardcodes that judge (`tau2/config.py`: `gpt-5.4-mini-2026-03-17`, at OpenAI, so it needs an `OPENAI_API_KEY`) and offers no option to change it. We have no such key, so with `--api-base-url` the judge is the model under test, at the same low effort and 4096-token cap as the simulated user (`--judge-llm-args` overrides both, merged key by key like `--user-llm-args`; `--judge-llm openai/<name>` picks another model on the same endpoint and key instead: a shared one by its hosted name, `--judge-api-base-url <url>` reaches the judge on an endpoint of its own when the model under test is served elsewhere (a job's own server, with the judge on the shared deployment: `chonk_sft` sets it to `https://api.swissai.svc.cscs.ch/v1`; the judge's key is `JUDGE_API_KEY`, default `local` (a server launched with `job.sh` checks no key, so the serving key is never sent to it; set `JUDGE_API_KEY` for a model on the shared API), named in its llm args as `os.environ/JUDGE_API_KEY`, never the key itself; it needs `--judge-llm`), or one you start with `python3 scripts/lm_eval_harness/launch_judge.py --preset gpt-oss-120b` by its served name, `openai/openai/gpt-oss-120b`, which the launcher looks up as `<user>/openai/gpt-oss-120b` in the endpoint's `/models` and stops when it is not served. Without `--judge-llm` it judges its own runs: a bias, so retail scores are not comparable with published ones). `scripts/custom/tau2_judge/sitecustomize.py` does it, on `PYTHONPATH` of the `tau2` process: it replaces the evaluator's model and arguments in memory and touches no upstream file. The same model judges the required information of a task (`communicate_info`), which upstream scores with a second, semantic judge (default `gpt-5.5`, resolved into each task's `CommunicateScoring.judge`; `results.json` keeps recording that default, not the model that judged). Only airline reaches it: its reward basis is DB and COMMUNICATE, and six tasks (3, 7, 11, 14, 18 and 23) carry `communicate_info`; without the shim those calls fail for want of an `OPENAI_API_KEY` and the six tasks end as infrastructure errors. A model is a worse fit than the one upstream was written for, so the shim also removes a markdown code fence around the judge's JSON (Chonk always adds one) and asks again, up to 8 times, when the reply does not parse or holds fewer verdicts than assertions (Chonk answers an empty list about half the time, which upstream would count as all assertions met); if it never gives a usable reply the evaluation raises, tau2 redoes the task, and nothing is scored without a judgement. Each retry prints a line. Without `--api-base-url` the judge stays upstream's own. airline's NL assertions are in its data but not in its reward basis, and telecom and banking_knowledge have no LLM judge.
- **Trials.** `--num-trials n` runs every task n times; the summary prints `avg_reward` and pass^k for k = 1..n (all k trials succeed, not pass@k). One trial is the default, so pass^1 is the plain mean.
- **Failed tasks.** tau2 retries a task up to 4 times and then gives up (`infrastructure_error`, no reward), and leaves it out of its own printed metrics, which would flatter a model that fails often. The cause of each such task is in `results.json` (`info.error`), so the summary separates them: when the model under test is to blame, because it replied with neither content nor tool calls (`AssistantMessage must have either content or tool_calls`; GLM-4.5-Air does it on 15 to 30% of telecom and banking tasks), the task counts as failed, reward 0, over all tasks (`n_agent_failures`). Any other cause is not the model's: a judge or user simulator that failed (a missing key, an empty reply of gpt-oss), a server error. Those tasks are not counted, they are listed (`n_unscored`) and the script exits 1: rerun them. The summary reports them: `n_agent_failures`, `agent_failures_by_cause` (`empty_reply`, `context_overflow`) and `excluding_agent_failures`, the figures tau2 itself would print with those tasks left out, so a published score can carry how many tasks the model failed to complete. Only two causes are taken as the model's: the empty reply, and a context overflow (`ContextWindowExceededError`) in the agent's own call, read from the error's traceback (`tau2/agent/`); an overflow in the user simulator's or the judge's call is another model's window and is rerun, and so is any error the script does not know: never scored.
- **Domain options.** `--retrieval-config` is banking_knowledge's retrieval pipeline. It defaults to `bm25` (keyword search, offline, free); tau2's own default embeds the documents with OpenAI and needs an `OPENAI_API_KEY`, which a job doesn't have. Banking scores with `bm25` are comparable between our runs, not with published tau2 numbers. Anything else goes after `--` to `tau2 run`, e.g. `intake` is voice-first, so a text run needs `-- --elicitation-strategy scaffolded`.
- **Results.** `<--workdir>/tau2-data/simulations/<--save-to>/results.json`: tau2 reads its data through a writable view in `--workdir` (the image is read-only), so give a `--workdir` on storage you keep when running in a job, since the container's `/tmp` is lost with it. The default run name is `<domain>-<date and time>`, a new run each time; the name of an earlier run resumes it, but only with the same domain, model and options. The summary is `scripts/custom/tau2_summary.py` (the launcher prints it; `python -m scripts.custom.tau2_summary <results.json> <trials>` prints it for any results file). The launcher does not upload to W&B; `python -m scripts.results.update_wandb_tau2 --entity apertus --project <suite name> --name <model> --results-file <results.json>` does, by hand (see how runs are uploaded in [suites](suites.md)): the model's W&B run gets the task `tau2_<domain>` with pass^k, `avg_reward`, `n_tasks`, `n_simulations`, `n_agent_failures` (`n_empty_replies`, `n_context_overflows`), `n_unscored` and, when some tasks were counted as the model's failure, `pass^1_excluding_agent_failures`, and the whole `results.json` (every conversation) is attached, gzipped, as the artifact `traces-tau2_<domain>` (a 65 MB file is about 10 MB; `--no-traces` skips it, a trace over `--max-trace-mb`, default 500, compressed is not uploaded).

`scripts/custom/` is for runners that do not go through one of the frameworks of this repository.

In a Slurm job: `sbatch scripts/custom/run_tau2_bench.sbatch <same arguments>` runs it CPU-only in the prebuilt image (or `containers/env.toml`) against an endpoint that is already serving, and without `--workdir` keeps the results in `logs/tau2/<job id>/`. [Suites](suites.md) launch their tau2 rows that way.

## The user and judge model of `chonk_sft`

The suite's tau2 rows name `openai/openai/gpt-oss-120b` as the simulated user, and the retail and airline rows also as judge (the two domains with an LLM judge: retail's NL assertions, and airline's six required-information checks, which would otherwise be judged by the model under test) (`reasoning_effort: low`, its lowest) at `{helper_url}`, which `suites run --helper-url <url>` fills in. Their sampling is stated on the rows too, `temperature` 0.6 and `top_p` 0.95 with `reasoning_effort: low` and `max_tokens` 4096 (`--user-llm-args`, `--judge-llm-args`). Without them the launcher copies the sampling of the model under test's profile to the user and judge, so these values would follow that profile; and the server sets none (vLLM's own defaults would be 1.0 and 1.0): they are sent with each request. The runs before 2026-11-23 sent the same values, inherited. Launch it once, for as long as the runs last, on its own node (`--tensor-parallel-size 4`; the tool parser is for the telecom user's phone tools):

```bash
scripts/direct_serving/job.sh --model /capstor/store/cscs/swissai/infra01/hf_models/models/openai/gpt-oss-120b \
  --served-model-name openai/gpt-oss-120b --environment containers/env_vllm_0.30.0.toml --nodes 1 --time 08:00:00 \
  --pre-launch-cmds 'export TIKTOKEN_ENCODINGS_BASE=<dir with o200k_base.tiktoken and cl100k_base.tiktoken>' \
  --framework-args '--tensor-parallel-size 4 --max-model-len 32768 --max-num-seqs 128 --enable-auto-tool-choice --tool-call-parser openai' \
  --eval 'hostname; sleep 28000' --submit
```

The job's node name and port 8080 are the helper URL (`http://<node>:8080/v1`). Compute nodes have no internet, so the two tiktoken vocab files must be downloaded beforehand (`https://openaipublic.blob.core.windows.net/encodings/<name>.tiktoken`): without them every request is a 500.
