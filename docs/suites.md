# Suites

A suite writes down a comparison once: its benchmarks, how each is repeated and scored, and the setups a model can run under. It lives in `configs/suites/<name>.json` (Apertus 2 suites in `configs/suites/apertus2/`, named `apertus2/<name>`); `scripts/common/suites.py` reads it and knows no model.

```bash
python -m scripts.common.suites show apertus2/chonk_sft   # title and setups
python -m scripts.common.suites plan apertus2/chonk_sft --setup apertus-1.5-70b-thinking
python -m scripts.common.suites flags apertus2/chonk_sft --setup apertus-1.5-70b-thinking --task ifbench
# --thinking --think-start-token '<|inner_prefix|>' --think-end-token '<|inner_suffix|>' --max-length 262144 --repeats 4
```

`show` prints the title and the setups. `plan` prints one row per benchmark (label, task, launcher flags, what it reports, the results key). Give `flags` output to the launcher next to `--task`. `run` starts a suite: see [Running a suite](#running-a-suite).

## File

| Part | Fields |
|---|---|
| `benchmarks` (list, table order) | `label` (the table row), `task`, `framework`, `repeats {n, via}`, `metric {label, key}`, optional `sampling`, optional `task_args` (inspect only), optional `flags` |
| `setups` (by name) | `max_length` (the model's maximal window), `sampling` (default profile), `flags` (by framework: thinking, chat format, tokenizer) |

- `repeats.via` is `flag` when the task has no repeats of its own and the launcher gets `--repeats n` (lm_eval) or `-- --epochs n` (inspect), or `task` when its yaml already repeats `n` times (AIME 8, the self-consistency tasks 4). The flag would apply the repeats twice, so nothing is passed.
- `metric.label` is what the table shows (`mean@4`); it must agree with `repeats.n`. `metric.key` is the key in a run's results that holds the value, `null` until it has been checked against a finished run.
- `sampling` names a profile of `configs/sampling_defaults.json` (`thinking`, `non_thinking`, `greedy`); a suite holds no temperature or top-p. A setup names its default and a benchmark may name another. A setup with a thinking flag (`--thinking`, `--enable-thinking`) is refused if a benchmark would sample with a temperature of 0. `plan` shows the profile per row; the launcher does not read it yet.
- `flags` is an object keyed by framework, with an entry (`[]` for none) for every framework the suite's benchmarks use: a thinking switch means `--thinking ...` to lm_eval and `--enable-thinking` to inspect. `flags_for` returns the setup's flags of the benchmark's framework, then what the suite adds: lm_eval `--max-length` and `--repeats`; inspect one `--task-arg key=value` per `task_args` entry and `-- --epochs n`. A setup's flags may not contain those. Inspect has no window flag, so `max_length` is only passed to lm_eval; keep the served `--max-model-len` equal to it.
- **Harbor rows** (`swe_bench`, `framework: harbor`) take the setup's `flags.harbor` (every setup needs the entry): the thinking switch where the setup has no `reasoning_effort`, and `--agent-kwarg model_info={"max_input_tokens": <window>}` so terminus-2 knows the window it may fill and summarises before it fills (`chonk_sft` tells it 32768 on the Chonk setups and Qwen3 32B, 131072 on GLM-4.5-Air and 262144 on the other setups, whatever the setup's `max_length` or served `--max-model-len`; an unaided agent ran out of room in the SWE-bench smoke runs at a 16384 window). A setup served with a smaller window than this gets errors from the server instead of a summary once the context passes it. The row's own `flags` carry `--sandbox opensandbox`. `run` launches it with `sbatch scripts/harbor/run_harbor_eval.sbatch --benchmark swe_bench ...`.
- `serving` (optional) lists the arguments the server itself needs, such as Apertus 2's `--tokenizer-mode apertus2 --reasoning-parser apertus2 ...` ([thinking](thinking.md#apertus-2-on-v1chatcompletions-temporary)); nothing in a suite runs them; `scripts/direct_serving/job.py --suite` appends them to the setup's `launch` arguments.
- `launch` (optional, `{model_path, environment, nodes, time, framework_args}`) says how the setup's model is served by [`scripts/direct_serving/job.py`](direct-serving.md#from-a-suite): the checkpoint, the serving EDF (a path in this repository), the nodes of the one replica, the wall time and the layout arguments (`framework_args`, a list; not `--model`, `--served-model-name`, `--host` or `--port`, which the launcher sets). The Chonk, GLM-4.5-Air and Nemotron setups and `apertus-1.5-70b-thinking` (the Apertus 1.5 release image with Ray, `containers/env_vllm_apertus1p5.toml`, 2 nodes TP4 x DP2) have one so far. Every one is served with `--max-model-len 262144`, except GLM-4.5-Air's, which is served with its native 131072 (the Harbor agent is told 32768 on the Chonk setups, whose window is served longer for BFCL v4). A server window of at least 32768 is what BFCL v4 needs: its memory categories send prompts over 16k tokens and a 16384 server answers them with HTTP 400. The checkpoint's `max_position_embeddings` is 16384, so vLLM only starts with `VLLM_ALLOW_LONG_MAX_MODEL_LEN=1` (the setup's `launch.env`) and what the model does past 16k is untrained. `env` (optional, variable name to string) is exported on every serving node before the server starts, ahead of `--pre-launch-cmds`. The partition, the plugin install and the sandbox are not part of it.
- `tokenizer` (optional, `{repo, revision, path}`) pins a tokenizer in a git repository by full commit sha. lm_eval rows get `--tokenizer <local copy>` (a setup's lm_eval flags may not hold `--tokenizer`); `flags` fetches the directory once into `$EVAL_ENV_CACHE_ROOT/tokenizers/<revision>/` (needs git access to the repository) and `plan` only shows where it will be. Apertus 2 needs this: its format has no Jinja template, and the verified tokenizer is `tokenizers/Apertus_2_instruct` of `swiss-ai/apertus-omni-tokenizer` at `b801ff1`, the revision `apertus-common` names.
- **Chat template** ([per framework](../README.md#chat-template)): a suite holds no template flag of its own; it is part of the setup's `flags`. lm_eval rows of a thinking setup get `--thinking`, which forces the template on; every lm_eval row here is generative, so no `--chat-template-by-type` is needed (add it to a setup that also runs log-likelihood tasks). Inspect, Harbor and EvalScope send chat requests and the server applies the template, so a setup's `inspect` flags carry only the thinking switch (`--enable-thinking`, which reaches the template as `chat_template_kwargs`).
- `reasoning_effort` (optional, per setup) becomes `--reasoning-effort <level>` on every lm_eval, inspect, evalscope and harbor row run under that setup, and the setup's flags may not set it. `chonk-lc-16k-v0.2-sft` uses `high` for all benchmarks: Chonk only reasons at `high` on non-math tasks (at `medium` its think frame is empty). Apertus 2 takes `low`, `medium` or `high`; the other setups set none.
- `flags` (optional, per benchmark) are launcher flags for that row under every setup, after the setup's own: `--sandbox opensandbox` for SWE-bench Verified. They may not hold what the suite produces (`--max-length`, `--repeats`, `--reasoning-effort`).
- `task_args` are the `-T` arguments of an inspect task, as strings, for example `{"fewshot": "0"}`; which ones exist depends on the task. The Chonk suite sets none.
- `name`, `title` and `description` are required. A malformed file is refused with the field named (`benchmarks[5] (aime24): repeats.via must be one of ...`).

## Running a suite

```bash
python -m scripts.common.suites run apertus2/chonk_sft --api-base-url https://api.swissai.svc.cscs.ch/v1 \
  --helper-url <gpt-oss server, see custom-tau2.md> --model chonk-lc-16k-v0.2-sft=<served name> --model qwen3-32b-thinking=<served name> \
  --qos highprio --partition highprio --limit 5 --no-wandb           # prints the commands
... --submit                                                          # runs them
```

Every (model, benchmark) pair is its own launch and Slurm job: 16 benchmarks and 2 models are 32 launches. `--model SETUP=SERVED_NAME` names a setup and the name its model is served under, once per model. An lm_eval row is one `launch_evaluations.sh single` launch (with `--backend openai` and `--api-model-name` when `--api-base-url` is given); an inspect row is one `sbatch scripts/inspect_ai/run_inspect_eval.sbatch`; a bfcl row (`bfcl_v3`, `bfcl_v4`) is one `sbatch scripts/custom/run_bfcl.sbatch --version v3|v4`, the official bfcl-eval package's generation, checkers and scores ([custom-bfcl](custom-bfcl.md)), with the setup's reasoning effort, the row's sampling profile and `--limit` as the number of entries per category; bfcl_v3's results key is its `overall`, bfcl_v4's is `overall_no_web_search`: the package's v4 formula with the memory score as the whole agentic group (web search is not run, so bfcl-eval has no overall for it; not the leaderboard's number, see custom-bfcl.md), and the groups and every category are in the W&B run. A tau2 row (one per domain: `airline`, `retail`, `telecom`, `banking_knowledge`; the task is the domain) is one `sbatch scripts/custom/run_tau2_bench.sbatch --domain <task>`, where `--limit` becomes `--num-tasks`, the agent samples with the setup's (or the row's) sampling profile as `--sampling-profile`, the thinking switch and effort are the agent's (the simulated user and the retail judge are the model under test at low effort: `chonk_sft` states the user's on each tau2 row as `--user-llm-args`, and `banking_knowledge`'s retrieval as `--retrieval-config bm25`; retail's judge as `--judge-llm openai/openai/gpt-oss-120b` at `--judge-api-base-url {helper_url}` and the same model as the simulated user (`--user-llm`, `--user-api-base-url`: one gpt-oss-120b launched in a job of its own, whose endpoint `suites run --helper-url <url>` fills in; not the model under test) with their pin as `--user-llm-args` and `--judge-llm-args`, see [custom tau2](custom-tau2.md#the-user-and-judge-model-of-chonk_sft)), the score is pass^1, and the results land in the row's log directory. `--qos` and `--partition` go to the launcher or to `sbatch`. The first line says how many launches there are (`32 launches: 2 models x 16 benchmarks`). Without `--submit` nothing runs; with it the launches start in order and the first failure stops the rest. Every launch but tau2's uploads to the W&B project named after the suite (`apertus/apertus2-chonk-sft`; `--no-wandb` skips it). Inspect, evalscope, bfcl, tau2 and Harbor rows write to `logs/<framework>/<suite>/<served name>/<task>` (`--logs-dir` / `--work-dir` / `--workdir`), so two runs of one model no longer share a directory; lm_eval's logs already sit under the W&B project. Other options (`--limit`, `--no-wandb`, `--api-model-name`) are passed to every launch. Other frameworks have no launcher yet and are refused.

Whoever launches decides where and how a model runs beyond its `launch` block (partition, account). To add a comparison, copy `apertus2/chonk_sft.json`; to add a kind of model, add a setup. The `tasks_*.txt` lists the launcher modes read are separate and unchanged.

## Every succeeded run is uploaded to W&B

The scores of each run that succeeded go to the suite's W&B project (`apertus/<suite name>`, `apertus/apertus2-chonk-sft` for `chonk_sft`): every metric of the run, plus a stratified handful of samples (a few correct and a few incorrect per task). The launchers do it themselves at the end of a run when a `WANDB_API_KEY` is set (every framework but tau2, whose launcher has no upload) (environment or `scripts/secrets.env`), and a launch that asks for the upload without a key fails in its [preflight](direct-serving.md#preflight). The full per-sample outputs and traces are not uploaded: they stay in the run's folder (lm-eval's `samples_<task>_<time>.jsonl`, BFCL's `result/` and `score/`, tau2's `results.json`, Harbor's trial folders).

A run that succeeded but was not uploaded gets uploaded by hand, to the same project and under the run name the launcher gives (one W&B run per model, all its tasks in it). That happens when the key was missing at the time, when the run belongs to a framework whose launcher has no upload (tau2), or when Slurm shows the job as FAILED although the evaluation finished: a job whose log ends `Evaluation finished` and then `error reading input file: Stale file handle` (its checkout was changed under it) has complete results. A run succeeded when its results file is complete; do not upload a partial one.

lm-eval, from the checkout, inside the eval image (`srun -A <account> -p debug -t 00:30:00 --environment=<the EDF of a job> bash -c '...'`; `eval_duration_seconds.txt` sits in the run folder):

```bash
source scripts/common/secrets.sh; export WANDB_API_KEY
export PATH=/opt/lm-eval-venv/bin:$PATH
python -m scripts.results.update_wandb_alignment --entity apertus --project <suite name> \
  --logs_root logs/lm_eval/<entity>/<project>/<run name>/harness/eval_<time>_<jobid> \
  --name <run name> --main_metrics <task> --eval_duration "$(cat <that folder>/eval_duration_seconds.txt)"
```

BFCL: `python -m scripts.results.update_wandb_bfcl --entity apertus --project <suite name> --name <model> --work-dir <the run's --workdir>`. tau2: `python -m scripts.results.update_wandb_tau2 --entity apertus --project <suite name> --name <model> --results-file <the run's results.json>`; `--traces` also attaches the whole `results.json`, gzipped, as the artifact `traces-<model>-tau2_<domain>` (off by default: the trace stays on the cluster). Harbor and EvalScope have `update_wandb_harbor` and `update_wandb_evalscope` (`--entity`, `--project`, `--name`, `--work-dir`), Inspect has `update_wandb_inspect` (`--name` and `--eval-log` of the run). The W&B run id is fixed per model name, so an upload to a run that exists updates its summary values and adds to its history; it does not create a second run.

Then read the values back (the W&B API shows them about a minute after the upload) and compare them with the results file: a run is done when its scores are in the project.
