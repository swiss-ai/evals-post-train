# EvalScope

`scripts/evalscope/run_evalscope_eval.sh` runs these benchmarks through [EvalScope](https://github.com/modelscope/evalscope); [Harbor](harbor.md) runs them too, with a different agent and scoring, so the scores differ.

| `--benchmark` | What | Images |
|---|---|---|
| `swe_bench` | SWE-bench Verified, 500 tasks (EvalScope's `swe_bench_verified_agentic`) | `swebench/sweb.eval.x86_64.*` (prebuilt, pulled) |
| `swe_bench_pro` | SWE-bench Pro **v1**, 731 tasks (see below) | `jefzda/sweap-images:<tag>` |
| `live_code_bench` | LiveCodeBench code generation (lite), `v6` slice by default (see below) | `python:3.11-slim` |
| `bfcl_v3` | BFCL V3 tool calling through EvalScope's own adapter (see below) | none |
| `bfcl_v4` | BFCL V4 tool calling, a signal only, not the leaderboard score (see below) | none |

Both use the same protocol. The agent works through a multi-turn bash loop inside the instance's own container and submits a `git diff`. EvalScope then applies that patch in a fresh container and runs the instance's tests. An instance counts as resolved when every fail-to-pass and pass-to-pass test passes. Pass `--benchmark swe_bench,swe_bench_pro` to run both in one go.

The script runs EvalScope from a cached venv of `requirements/evalscope-runtime.lock` (every package pinned, see `scripts/common/locked_venv.sh`). It can't share the lm-eval/Inspect environment because EvalScope's `math-verify` pin conflicts with that environment's `antlr4` pin. The script takes `--model`/`--api-base-url` and uses the same serving-key fallback as `run_inspect_eval.sh`. It writes EvalScope's own outputs plus a `summary.json` to `logs/evalscope/<name>/`. Besides the scores, `summary.json` records what's needed to reproduce the run: the EvalScope version, the Hugging Face dataset revision for each benchmark (both pinned in `scripts/evalscope/run.py`, override with `--dataset-revision <benchmark>=<sha>`) and the `SWE-bench_Pro-os` commit (EvalScope pins `ca10a60`).

**LiveCodeBench.** `--benchmark live_code_bench` runs EvalScope's `live_code_bench`: one 0-shot prompt per problem, the code extracted from the reply and run against the problem's tests in a sandbox pool (`python_executor`, 6 s per test). EvalScope's copy of the dataset exists only on ModelScope, so this benchmark loads from there (`dataset_hub: modelscope`), pinned to a commit in `scripts/evalscope/run.py` (`--dataset-revision live_code_bench=<sha>` overrides). That also means it can't share a run with the SWE-bench benchmarks. `--subset` picks the slice: the default `v6` is the problems released in release 6 only: 175 problems with contest dates 2025-01-04 to 2025-04-06 (AtCoder and LeetCode; 43 easy, 52 medium, 80 hard), the same as the official `test6.jsonl`. Papers' "LiveCodeBench v6" figures use different windows, so compare only with the same release and date range; `release_v6` is every problem up to release 6, and `release_v5`, `v5` etc. work the same way. The score is `pass@1`. `--sandbox docker` and `opensandbox` work; `--sandbox k8s` has no sandbox pool and is refused. There are no reference solutions, so `--gold` is refused too.

**BFCL v3.** `--benchmark bfcl_v3` runs EvalScope's `bfcl_v3` adapter: the test data is EvalScope's copy of the dataset on ModelScope (`AI-ModelScope/bfcl_v3`, so `dataset_hub: modelscope` and no shared run with the SWE-bench benchmarks), pinned to its `master` commit `18dfeab` in `scripts/evalscope/run.py` (`--dataset-revision bfcl_v3=<sha>` overrides), and the scoring is the `bfcl-eval` checkers (the same `bfcl-eval==2026.3.23` as v4; the adapter's own docs ask for `2025.10.27.1`, but every function it imports exists with the same signature in 2026.3.23). The default subsets are the adapter's 17 v3 categories (`simple`, `java`, `javascript`, `multiple`, `parallel`, `parallel_multiple`, `irrelevance`, the `live_*` ones and four `multi_turn_*`), with `OVERALL` computed the way the leaderboard's v3 table does. Unlike v4, EvalScope's own model client makes the requests, so the whole generation config reaches the server (`reasoning_effort`, the thinking flags' `extra_body`, `--top-p`, `max_tokens`) and `bfcl_request.py` is not involved. Native function calling on `/v1/chat/completions` is the default; `--extra-param is_fc_model=false` is prompt mode. `--extra-param underscore_to_dot=false` turns off the dot-to-underscore conversion of function names (default true, as in [EvalScope's BFCL v3 page](https://evalscope.readthedocs.io/en/v1.5.0/third_party/bfcl_v3.html), which also runs with `temperature` 0, `max_tokens` 32000 and `parallel_tool_calls` true: pass the last two with `--generation-config '{"max_tokens": 32000, "parallel_tool_calls": true}'`; the runner sets none of them itself). No sandbox, no `--gold`. `lm_eval`'s `bfcl_v3_fc` is a separate implementation (harness fork), so its scores need not match this one's. Smoke-tested once (2026-11-19, `chonk-lc-16k-v0.2-sft-32k`, thinking `high`, native calls, `simple`, `live_relevance` and `multi_turn_base` with `--limit 5`): it ran cleanly with no evaluation errors, and the five `multi_turn_base` failures were the model's own mistakes in the transcripts, not harness faults. Scores have not been compared with `bfcl_v3_fc` yet; do that on one model before trusting the numbers.

**BFCL v4 (a tool-call signal, not the original benchmark yet).** `--benchmark bfcl_v4` runs EvalScope's `bfcl_v4`, which wraps the official [`bfcl-eval`](https://pypi.org/project/bfcl-eval/) package: the test data, the OpenAI handler that calls the model and the scorer all come from it, pinned to `bfcl-eval==2026.3.23` (`requirements/evalscope-bfcl.txt`, installed without dependencies because it pins numpy 1.26 against the lock's numpy 2; it works with numpy 2). There is no Hugging Face dataset revision: the package version is the pin, and `summary.json` records it (`bfcl_eval_version`) with `is_fc_model`. Nothing runs in a sandbox, so `--sandbox` has no effect, and `--gold` is refused. The model gets native function calling on `/v1/chat/completions`; `--extra-param is_fc_model=false` switches to BFCL's prompt mode (functions in the prompt, the reply parsed as Python). `bfcl-eval`'s handler sends only the temperature from the generation config, so `scripts/evalscope/bfcl_request.py` adds `reasoning_effort` and `extra_body` (the thinking flags' chat-template kwargs, `min_p`) to every request it makes; `--top-p`, `--top-k` and `max_tokens` in `--generation-config` still do not reach the model, and the runner warns when one was asked for.

The default subsets are the leaderboard's without `web_search_base`/`web_search_no_snippet` (they need a SerpAPI key and network), so `OVERALL` is not the leaderboard's number and the agentic aggregate covers memory only. Treat the scores as a tool-calling signal to compare between our own runs, not as leaderboard results, until web search runs and a score has been checked against a known model; per category they are what `bfcl-eval` computes. `--subset` picks others, but the runner refuses `web_search_*` without `SERPAPI_API_KEY` in the environment (never `--extra-param`, which EvalScope writes to its log and `task_config.yaml`, so the runner refuses it there too) and `memory_vector` in an environment without `sentence-transformers` and `faiss-cpu`: left to run they would score every sample 0 and still exit 0. `memory_vector` embeds with `all-MiniLM-L6-v2` (CPU torch is in the lock), which is downloaded from Hugging Face on first use, so the run needs access to it. Java and JavaScript scoring needs `tree_sitter`, in the lock. **Concurrency:** bfcl_v4 runs 32 samples at once unless `--max-concurrency` says otherwise (the other benchmarks 4, as their sandboxes are the limit); 64 was 6% faster than 32 on 102 samples. The memory categories run a prerequisite chain of inferences per scenario, one after another, so they are slow whatever the concurrency: run them as their own job with `--subset` (`memory_kv` with `--limit 2` was still in its prerequisites after 25 minutes). **Context window:** the memory categories send prompts over 16k tokens, so a server with a 16384 window answers those samples with HTTP 400, and they score 0 without failing the run (`evaluation_errors` stays empty); serve the model with at least 32k, or leave `memory_*` out with `--subset`. Qwen2.5-7B-Instruct at 16k hit this on `memory_kv`.

**Base models (`--completions`).** EvalScope only calls `/v1/chat/completions`, so the server wraps the prompt in a chat template, which a base model lacks. `--completions` follows LiveCodeBench's own base-model setup (`lcb_runner` `GenericBase`) instead: the prompt goes as plain text to `/v1/completions` (`scripts/evalscope/completions_model.py`, EvalScope eval type `openai_completions`; system messages are dropped), and it is the official one-shot prompt (one worked example, then the problem, no system message; `scripts/evalscope/lcb_base.py`, examples copied from LiveCodeBench, MIT). Generation stops at `###` with a 2000-token limit, the official runner's defaults, and the reply is taken as the code itself with no fence needed. `--generation-config '{"max_tokens": ..., "stop_seqs": [...]}'` overrides those two. The other flags (`--subset`, sampling, `--sandbox`) work as without it. Only `live_code_bench` has a base-model prompt.

SWE-bench is scored by `scripts/evalscope/swe_bench_scoring.py`, not EvalScope's own scorer. The evaluation itself is the same: the same `swebench` test spec, eval script, patch-apply fallbacks and grading. EvalScope's version uses the Docker SDK directly, which never pulls the image and doesn't work without a Docker daemon. This one creates its container through EvalScope's sandbox layer, so it pulls the image and works on both `--sandbox` engines.

**This is SWE-bench Pro v1.** EvalScope implements v1: 731 tasks, `jefzda/sweap-images`, and the v1 run scripts. On 2026-09-22 Scale released V2, made it the dataset's `default` config, and kept v1 as config `v1`. V2 has 642 validated tasks shipped as [Harbor](https://github.com/harbor-framework/harbor) tasks with `ghcr.io/scaleapi/swe-bench_pro-v2` images. Scoring V2 rows with the v1 pipeline fails even the reference patches, because the test patch it applies doesn't exist in the v1 images. The runner therefore pins the dataset to its last v1 commit, `7ab5114` (override with `--dataset-revision swe_bench_pro=<sha>`). Its scores are v1 numbers and aren't comparable with V2 ones.

Every sample runs in its own sandbox container (`--sandbox`):

- `docker`: EvalScope's own path, using a local Docker daemon.
- `k8s`: one unprivileged pod per sandbox in the current namespace, via `scripts/common/k8s_sandbox.py`, with no Docker daemon needed. The service account needs `create`/`get`/`delete` on `pods` and `create`/`get` on `pods/exec`. The images are linux/amd64, so the pods are pinned to amd64 nodes. Pod settings come from `SANDBOX_K8S_*` env vars (see the module docstring). The runner itself doesn't have to run in the cluster: from a laptop, `--sandbox k8s` uses your current kubeconfig context, and `SANDBOX_K8S_NAMESPACE` picks the namespace (e.g. on Breithorn). Pods started that way have no owner pod, so if the runner dies, delete leftovers with `kubectl delete pods -l sandbox-run=<SANDBOX_K8S_RUN_LABEL>`.
- `opensandbox`: one Kata microVM per sandbox, with its own kernel, through an OpenSandbox server (`scripts/common/opensandbox_sandbox.py`), with no Docker daemon and no Kubernetes access. It needs `OPENSANDBOX_API_KEY` (in the environment or `scripts/secrets.env`). `OPENSANDBOX_DOMAIN` defaults to Breithorn's Kata endpoint, the same server Harbor's `--sandbox opensandbox` uses. `OPENSANDBOX_LOG_DIR`, if set, keeps each sandbox's diagnostic events and logs (the server's own, which go with the sandbox) as `<sandbox id>.log`, saved just before it is killed. The agent loop's sandboxes reach only package indexes (PyPI, conda, Debian/Ubuntu mirrors, npm; `scripts/common/swe_bench_egress.py`), not GitHub and the other hosts that have each task's fix, as SWE-bench's leaderboard checklist asks. Scoring sandboxes keep open network, as under Docker. The model endpoint's host is allowed too, for agents that run inside the sandbox. EvalScope's external runners (Claude Code, Codex, ...) install themselves from other hosts, so they need `--agent-network public` (open network for the agent too). `summary.json` records `agent_network`. With `docker` and `k8s` every sandbox has open network. Sandboxes carry a `sandbox-run` label unique to the run (`OPENSANDBOX_RUN_LABEL`); the runner deletes any left when the run ends. If the runner is killed outright, they stay until their 24-hour timeout.

Notes:

- The default `swe_bench_toolcall` strategy needs a served model with tool calling (vLLM `--enable-auto-tool-choice` plus a parser, sglang `--tool-call-parser`). `--strategy swe_bench_backticks` drives the agent through plain text instead.
- The step cap is 250 by default, and each instance's test run can take up to `eval_timeout` (3600 s). A full run is long.
- Each sandbox gets 2 CPUs. With `--sandbox docker` it gets 4 GiB (ms-enclave's default). Some SWE-bench Pro instances need more: teleport's tests peak at about 7.4 GiB, element-web fails the same way at 4 GiB, and EvalScope's docs mention NodeBB. With `--sandbox opensandbox` it gets 8 GiB, which is the microVM's memory. `--sandbox k8s` defaults to an 8 GiB limit with a 4 GiB request (`SANDBOX_K8S_MEMORY_REQUEST=4g`): an 8 GiB request often doesn't schedule on Breithorn's amd64 nodes, while this one does and still lets a pod grow to 8 GiB. Memory above the request isn't guaranteed: under node memory pressure such pods are evicted first. Setting `memory_limit` in `--sandbox-config` replaces both defaults, and the request then equals the limit unless `SANDBOX_K8S_MEMORY_REQUEST` is set.
- A sample whose evaluation fails for an infrastructure reason still scores as unresolved in EvalScope's report. Examples: an OOM-killed container, a pod that never schedules, or the cluster API dropping out. Such samples are listed under `evaluation_errors` in `summary.json`, and the run then exits non-zero. A patch that doesn't apply, or tests that time out, are the model's failures and aren't counted there.
- `--limit N` takes the first N instances, which are mostly from one repository. Add `--shuffle` (fixed seed 42) for a sample across repositories that is still the same on every run.
- The instance images total many GB and are pulled from DockerHub, so expect pull rate limits. Set `SANDBOX_K8S_IMAGE_PULL_SECRET` for an authenticated pull.

```bash
# Pipeline check without a model: score each instance's reference patch (every instance should resolve)
scripts/evalscope/run_evalscope_eval.sh --benchmark swe_bench,swe_bench_pro --gold --limit 20 --shuffle

# Smoke test: two instances of each benchmark, two sandboxes at a time
scripts/evalscope/run_evalscope_eval.sh --benchmark swe_bench,swe_bench_pro --model <served model with tool calling> \
  --api-base-url https://api.swissai.svc.cscs.ch/v1 --limit 2 --max-concurrency 2 --no-wandb

# Inside a k8s Job (the default there): pods on amd64 nodes, more memory per sandbox
scripts/evalscope/run_evalscope_eval.sh --benchmark swe_bench_pro --model <served model> --api-base-url <url> \
  --sandbox k8s --sandbox-config '{"memory_limit": "8g", "cpu_limit": 4}' --max-concurrency 8

# From a laptop, sandboxes as pods in a Breithorn namespace; patient retries for a shared, rate-limited key.
# Keep the laptop awake (caffeinate -i on macOS): a sleeping laptop loses DNS and the run's samples error out.
SANDBOX_K8S_NAMESPACE=<namespace> SANDBOX_K8S_RUN_LABEL=my-run \
  caffeinate -i scripts/evalscope/run_evalscope_eval.sh --benchmark swe_bench,swe_bench_pro \
  --model CSCS-Inference/swiss-ai/Apertus-v1.5-8B --api-base-url https://api.swissai.svc.cscs.ch/v1 \
  --sandbox k8s --limit 1 --max-concurrency 1 --no-wandb \
  --generation-config '{"retries": 100, "retry_interval": 60}'
```

**On Clariden:** the nodes are aarch64 and have no Docker, so `scripts/evalscope/run_evalscope_eval.sbatch` runs EvalScope and the agent in a CPU job, with the sandboxes as Breithorn pods (`--sandbox k8s`, namespace `rob-poc` by default). The kubeconfig on Clariden authenticates through an OIDC login (kubelogin) that a batch job can't renew. Log in first (`kubectl get pods` works on the login node), and keep the run within the token's lifetime. The pods are labelled `sandbox-run=evalscope-<job id>`, and the job deletes the ones left at the end. Three minutes before the time limit it stops the run; EvalScope writes `summary.json` only when a run finishes, so a stopped run has none.

```bash
sbatch -p debug -t 1:00:00 scripts/evalscope/run_evalscope_eval.sbatch --benchmark swe_bench,swe_bench_pro --gold --limit 2
```

The results go to W&B whenever `WANDB_API_KEY` is set (in the environment or `scripts/secrets.env`), by default to `apertus/e-p-t-pool`; `--wandb-entity`/`--wandb-project` change that, and `--no-wandb` (or `WANDB_MODE=disabled`) skips the upload, e.g. for a smoke test. They are uploaded as one run named `--name` (`--gold` runs are not uploaded), through the same `ModelEvaluation` structure and `upload_multi_model_results` as the other frameworks. Each benchmark gets its `accuracy` (the share of instances resolved), `n_samples` and `n_errors`, plus a few resolved, unresolved and failed-evaluation instances as samples (tests passed of those required, the failing tests, tokens, the patch). `accuracy` counts failed evaluations as unresolved, so with `n_errors` > 0 it is too low. To upload an existing run: `python -m scripts.results.update_wandb_evalscope --entity <e> --project <p> --name <name> --work-dir logs/evalscope/<name>` from the EvalScope venv.
